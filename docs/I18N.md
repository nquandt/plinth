# Localization design (draft)

This document is the design of localization in Plinth: app text in more than one language, number and date formats of the user's locale, plural rules, and right-to-left layout. It covers checklist items U8, U9 and L5 in `docs/PRODUCTION.md`. 1.0 needs localization (owner decision PR-Q2).

Status: design draft, 2026-10-07. Steps 1 and 2 of §4 are built (2026-10-08, core 1.13): §3.6 and §3.7 tell what was built and the decisions. The other steps are not built yet.

## 1. Goals

1. An author writes an app one time and gives translations as data. The same `.plnt` shows the user's language on every host.
2. Numbers, dates, times, lists and plurals follow the user's locale on every host, with the same result on each host.
3. The runtime-owned UI (Level 1 controls, the date picker, the back button, the stop banner, the consent window, the host dialogs) is in the user's language without work by the author.
4. A right-to-left language (Arabic, Hebrew, Persian, Urdu) mirrors the layout.
5. App code stays small. The core has no Unicode or locale tables (HANDOFF §6).

## 2. Today

- All app text is in the language that the author writes.
- `plinth:time` `formatDate` has English month and day names only (`std/time.d.ts`).
- Runtime-owned text is English and is hard-coded in each host: for example "Back", "OK", "Cancel", "This app stopped", "Allow" (`crates/plinth-ui/src/render.rs`, `crates/plinth-ui/src/calendar.rs`, `crates/plinth-host-desktop/src/consent.rs`, `web/dom-renderer.js`, `web/frame-host.js`).
- SPEC §4.7 names a `plinth:locale` module, and SPEC §8.5 allows locale calls to be synchronous. Step 1 (§3.6) added the module with `locale()` and `direction()`. Step 2 (§3.7) added the formatting functions.

## 3. Model

### 3.1 The locale

- The host gives the app one locale: a BCP 47 tag such as `de-CH` or `ar-EG`. It comes from the OS (desktop, mobile) or `navigator.languages` (web). The user can set another locale for each app in the Hub.
- The host picks the best match between the user's preferred languages and the languages that the app supports (§3.2), with the usual fallback (`de-CH` → `de` → the app's default language).
- `plinth:locale` gives the app the result: `locale(): string`, `direction(): "ltr" | "rtl"`. A change of the OS locale while the app runs sends an event, and the app's text updates through signals (§3.3).

### 3.2 App text: message catalogs

- The author keeps one catalog for each language in `locales/<tag>.json` in the project. `plinth build` puts them into the package as `assets/locales/<tag>.json` (a new optional entry kind needs no new package format; `docs/COMPATIBILITY.md` §4).
- `plinth.toml` names the default language: `default-locale = "en"`. The catalog of the default language is complete. Other catalogs can be partial: a missing message falls back to the default language.
- A message has an id and a text in a subset of ICU MessageFormat: arguments (`{name}`), plurals (`{count, plural, one {# file} other {# files}}`), select (`{gender, select, …}`), and number and date arguments (`{total, number, currency/EUR}`, `{when, date, medium}`).
- In code, the author calls `t("files.count", { count })`. `t` comes from `plinth:locale` and returns a `string` signal value, so the text updates when the locale changes.
- **Checks at build time** (the compiler, closed world): the first argument of `t` is a string literal; the id exists in the default catalog; the argument names and kinds match the message. An error has a PL code and a golden test. A catalog with an unknown id, a syntax error or a missing argument gives a warning. This catches most translation defects before the app ships.
- The compiler can generate a typed module from the default catalog later, for completion in the editor (open question I18N-Q3).

### 3.3 Formatting: in the host, not in the core

Locale data (number symbols, month names, plural rules for about 200 languages) is large. The core must stay free of Unicode and locale tables, and app code must stay small. So the host formats:

- **Web:** the browser's `Intl` API (`NumberFormat`, `DateTimeFormat`, `PluralRules`, `ListFormat`, `RelativeTimeFormat`, `Collator`).
- **Desktop and mobile:** ICU4X in the native host (a Rust crate with compiled locale data, maintained by the Unicode Consortium). It is the same data source as the browsers' `Intl` in most cases, so results agree.
- `plinth:locale` gets new host functions (a new interface `locale` in `app.wit`, with a new core minor version): `format-number(value, options)`, `format-date(ms, options)`, `plural-category(value, type)`, `format-list(items, type)`, `compare(a, b)`. They are synchronous (SPEC §8.5 allows it for locale calls).
- The core's message formatter (the ICU MessageFormat subset of §3.2) is small: it parses the message and calls the host functions for plurals, numbers and dates. It holds no locale data.
- `plinth:time` `formatDate` keeps its pattern tokens. A new `formatDate(ms, { dateStyle, timeStyle })` form goes through the host. Month and day names in the old pattern form stay English (compatibility rule: no change of behavior).
- A test runs the same formatting calls on the desktop host (ICU4X) and the web host (`Intl`) and compares the results for a list of locales. A difference is a defect, or it is listed as a known difference.

### 3.4 Runtime-owned text

- Every host-owned string gets an id and goes into one catalog in the repository: `locales/runtime/<tag>.json`. The desktop host embeds the catalogs; the web host loads the catalog of the page's locale.
- Level 1 controls that show text of their own (the date picker's month names, "Back", "OK", "Cancel", "Search", the stop banner and its reasons, the consent window, the update prompt, the host dialogs) take it from this catalog, in the app's locale.
- The first version ships English and the languages that volunteers translate. A missing translation falls back to English.

### 3.5 Right-to-left layout (U9)

- `direction()` is `rtl` for a right-to-left locale. The host mirrors the layout of the whole app: the start edge is on the right, rows run from right to left, the navigation and the back arrow mirror, and text aligns to the start edge.
- Level 2 primitives use logical names (`start`, `end`), not `left` and `right`, so the same app mirrors without changes. Check every Level 2 prop for physical names before 1.0; a physical name needs a logical replacement and a deprecation (`docs/COMPATIBILITY.md` §6).
- Text of mixed direction (an English word in Arabic text) uses the Unicode bidirectional algorithm. The browser does it on the web. On the desktop, gpui-ce's text system must support it: check this first (I18N-Q1); it is the largest risk.
- `Canvas` drawings do not mirror. An app reads `direction()` if it must draw differently.
- The web host sets `dir="rtl"` and `lang` on the app's root element.

### 3.6 Step 1: what is built

Decisions for the details that §3.1 did not give (the simple option each time):

- **WIT.** A new interface `locale` with `tag: func() -> string` and `is-rtl: func() -> bool` (core 1.13). Both are synchronous. No capability: the locale is a small fingerprint (the browser gives `navigator.language` to every page), as the time zone, which also needs no capability.
- **Core functions.** `locale_tag` and `locale_direction` (`ADDED_IN` 13). Only an app that imports `plinth:locale` needs core 1.13 because of them.
- **The event.** No new event code: an older core cannot skip an unknown code (it traps on it). The host sends the `lifecycle` event with a new kind 4, "locale changed", with no payload. Cores 1.12 and older ignore a kind that they do not know. SPEC §8.4 lists kinds 0 to 3 only; the owner must add kind 4 to its table.
- **Reactive, not a callback.** The core keeps a counter signal for the locale (as for `isActive()`). `locale()` and `direction()` read the signal and then ask the host. The event increments the counter, so each text, `computed` value and `effect` that read the locale runs again. The value itself is not kept in the core; the host gives it at each read.
- **The direction** comes from the host, from fixed lists (a right-to-left script subtag, else a right-to-left language). The desktop (`crates/plinth-runner-wasmtime/src/locale.rs`) and the web (`web/plinth-web.js`) have the same lists, and both tests check the same cases.
- **The tag.** The host normalizes it (`en_US.UTF-8` → `en-US`, `zh_hans_cn` → `zh-Hans-CN`) and gives `en-US` when it finds none. The host does not yet match it against the languages of the app (§3.1, second item): that needs the catalogs of step 3.
- **Desktop.** The OS locale (`sys-locale`), read at the first call. `PLINTH_LOCALE` overrides it for manual tests. The host reads the OS locale again each time the app window comes to the foreground and sends the event if it changed (a user changes the setting in another window). Tests fix the locale with `Guest::set_locale` and change it with `Guest::change_locale`.
- **Web.** The page gives its locale (`navigator.languages[0]`) to the frame in the `start` message, and sends each `languagechange` of the page (`AppFrame`, used by the web Hub and by web exports). Thus the page can later give a locale that the user chose for each app (I18N-Q5). The frame sets `lang` and `dir` on the root element of the app (`applyLocale`) and gives the locale to the Worker. The stand-alone page uses its own locale, or `?locale=<tag>`.
- **Tests.** `crates/plinth-compiler/tests/locale.rs` (both engines; five locales, the change event, the core version) and `web/test/run-locale.mjs`.

Gaps of step 1:

- The desktop host does not watch the OS setting while the window stays in the foreground (for example `WM_SETTINGCHANGE` on Windows). It reads it again only when the window comes back to the foreground.
- The desktop host does not mirror the layout yet (step 5).
- The web Hub has no setting for the locale of each app yet (I18N-Q5).

### 3.7 Step 2: what is built

Decisions for the details that §3.3 did not give (the simple option each time):

- **The API** (`std/locale.d.ts`): `formatNumber(value, options?)`, `formatDate(ms, options?)`, `pluralCategory(value, type?)`, `formatList(items, type?)` and `compare(a, b)`. All are synchronous and reactive: they read the locale signal of §3.6, so a text that calls them changes when the locale changes. The options are the same on both hosts, and there are few of them:
  - `formatNumber`: `style` ("decimal", "percent", "currency"), `currency` (an ISO 4217 code), `minimumFractionDigits` and `maximumFractionDigits` (0 to 20), `useGrouping`, `notation` ("standard", "compact"). The currency sets the fraction digits of "currency". The digit options and `useGrouping` apply to "decimal" and "percent". "compact" is the short form ("1.2K") and applies to "decimal" only. The long compact form ("1.2 thousand") is not in the API.
  - `formatDate`: `dateStyle` ("full", "long", "medium", "short") and `timeStyle` ("medium", "short"). With neither, `dateStyle` is "medium". The time zone is the local time zone of the host (the same as `plinth:time`). `timeStyle` "full" and "long" are not in the API: they show the name of the time zone, and the desktop host knows only the offset.
  - `pluralCategory`: "cardinal" (the default) or "ordinal". The result is one of the six CLDR categories.
  - `formatList`: "conjunction" (the default) or "disjunction", in the wide form ("a, b, and c").
  - `compare`: the collation of the locale with the default strength. The result is -1, 0 or 1. Use it in `sort`.
- **`formatDate` of `plinth:time`** keeps its pattern form and its English names (§3.3). The locale form is `formatDate` of `plinth:locale`. An app that needs both imports one of them with another name.
- **The options are an object literal at the call** (as `NotifyOptions`). The compiler checks each field and makes JSON text, for example `{"style":"percent"}`. The host reads the JSON text, so a new option needs no new WIT function. The items of `formatList` go to the host as a JSON array.
- **WIT:** five new functions in the interface `locale` (core 1.13): `format-number(value: f64, options: string) -> string`, `format-date(ms: f64, options: string) -> string`, `plural-category(value: f64, kind: string) -> string`, `format-list(items: string, kind: string) -> string`, `compare(a: string, b: string) -> s32`. Core functions: `locale_format_number`, `locale_format_date`, `locale_plural`, `locale_format_list`, `locale_compare` (`ADDED_IN` 13).
- **No input traps or throws.** A value that is not finite gives "" (`pluralCategory` gives "other"). A currency code that is not three letters gives the "decimal" style. The host ignores bad JSON, an unknown option and an unknown value. A tag that the formatter cannot read gives `en-US`.
- **Desktop** (`crates/plinth-runner-wasmtime/src/locale_format.rs`): ICU4X 2.3 with its compiled data for all locales (I18N-Q2: all locales; about 2.5 MB of code and data in a release build). The crates are `icu_decimal`, `icu_datetime`, `icu_calendar`, `icu_time`, `icu_plurals`, `icu_list`, `icu_collator`, `icu_locale_core` and `icu_experimental` 0.6 (the currency and percent formatters are not in a stable crate yet). All have the license Unicode-3.0. Each call makes its formatter again (some microseconds). A cache for each locale can come later.
- **Web** (`web/plinth-web.js`, `formatNumberIntl` and the functions after it): `Intl.NumberFormat`, `Intl.DateTimeFormat`, `Intl.PluralRules`, `Intl.ListFormat` and `Intl.Collator`, in the Worker that runs the app, with the locale of step 1 (not `navigator.language` of the Worker).
- **U+202F in dates.** CLDR puts a narrow no-break space (U+202F) in some date and time patterns, for example before "AM" in English and before "г." in Russian. ICU4X gives it. Chrome and Node give a space (U+0020) there; other browsers can give U+202F. Both hosts replace U+202F with a space in the result of `formatDate`, so all hosts and browsers give the same text. Numbers keep U+202F (the group separator of French) on both hosts.
- **The test.** `crates/plinth-compiler/tests/locale_cases.txt` has 56 calls with the text in 8 locales (en-US, de-DE, fr-FR, ar-EG, ja-JP, hi-IN, pl-PL, ru-RU). `tests/locale_format.rs` (wasmtime and wasmi) and `web/test/run-locale.mjs` (Node 22: ICU 78, CLDR 48) build one app with all calls, start it in each locale and compare each text with the file, also after a locale change. The comparison is exact: the file writes U+00A0, U+202F, U+200E, U+061C and the other invisible characters as `\u{…}`.

Known differences (the case file records each one with its reason; 8 of 448 texts):

| Case | Locale | Desktop (ICU4X 2.3) | Web (Node 22, CLDR 48) | Reason |
|---|---|---|---|---|
| `currency_usd`, `currency_negative` | pl-PL | `1234,50 US$` | `1234,50 USD` | `icu_experimental` 0.6 uses the root symbol. CLDR 48 has the ISO code for this locale. |
| `currency_jpy` | fr-FR, pl-PL | `1 235 JP¥` | `1 235 JPY` | The same. |
| `percent`, `percent_digits` | ar-EG | `٢٦‎%‎` (the Latin `%` with U+200E) | `٢٦٪؜` (U+066A with U+061C) | The percent data of `icu_experimental` 0.6 for the Arabic digits. |
| `date_short`, `date_short_time_medium` | pl-PL | `08.10.2026` | `8.10.2026` | ICU4X 2.x makes the date from a skeleton (`dd.MM.y`). The browser uses the CLDR short date pattern (`d.MM.y`). |

All other results are the same: also the Arabic and Devanagari digits and marks, the Indian grouping (`12,34,567`), the Polish grouping rule (no group for 4 digits), the compact forms, the plural rules and the collation. When a browser or ICU4X updates its CLDR data, a case can change: then update the case file and this table.

Gaps of step 2:

- `icu_experimental` is not stable: its API can change in a minor version. Move to the stable crate when ICU4X releases currency and percent formatting.
- On the desktop, the date and the time have one length (ICU4X): the date style decides when both are given. All tested combinations give the same text as `Intl`.
- `RelativeTimeFormat` ("in 3 days") is not in the API yet (§3.3 names it for the web).

## 4. Steps

1. `plinth:locale` `locale()` and `direction()`, and the locale event. Hosts: OS and browser locale. **Done** (§3.6).
2. Host formatting functions (ICU4X on the desktop, `Intl` on the web) and the cross-host comparison test. **Done** (§3.7).
3. Message catalogs, `t()`, the MessageFormat subset in the core, and the build-time checks.
4. Runtime-owned text in catalogs on both hosts.
5. Right-to-left layout: logical Level 2 names, mirroring on both hosts, bidirectional text on the desktop.
6. Tools: `plinth i18n extract` (a list of ids that the code uses and that a catalog does not have), and a pseudo-locale for tests (`en-XA`: longer text with accents, to find cut-off and hard-coded text).
7. Docs: `docs/guides/localization.md`, and updates to `docs/LIMITS.md` and `docs/PRODUCTION.md`.

## 5. Open questions

| # | Question | Notes |
|---|---|---|
| I18N-Q1 | Does gpui-ce support bidirectional text and right-to-left layout? | If not, it is work in the owner's fork, and the largest risk of this design. |
| I18N-Q2 | How much ICU4X data does the desktop host embed? | All locales, or a set with a download for the rest. There is no runtime size limit (owner decision 6), so "all" is possible. |
| I18N-Q3 | Should the compiler generate a typed module from the default catalog? | Better editor completion; more build work. |
| I18N-Q4 | Is the ICU MessageFormat subset enough, or is MessageFormat 2 better? | MessageFormat 2 is the newer Unicode standard; tool support is still small. |
| I18N-Q5 | Can a user set the locale for each app, or only for the whole host? | The Hub can offer both. |
