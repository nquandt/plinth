# Plinth web host (spike)

Runs the SAME `.plnt` package and the SAME runtime core file the desktop
host uses, directly in a browser. No bundler, no build step, no npm
dependency: plain ES modules (SPEC.md §18.3, the "browse mode" side-module
model — no static linking happens in the browser).

## Try it

```sh
cargo build -p plinth-cli
target/debug/plinth.exe build examples/counter      # writes examples/counter/dist/counter.plnt
target/debug/plinth.exe core export target/core.wasm # the runtime core, as a plain core wasm module

npx -y http-server . -p 8080
# then open:
# http://localhost:8080/web/index.html?app=../examples/counter/dist/counter.plnt&core=../target/core.wasm
```

Any static file server works (the browser needs CORS-friendly `fetch` of
`.plnt` and `.wasm`, so `file://` will not do). `npx http-server` is the
simplest option; there is no `plinth web` CLI subcommand yet (left for a
follow-up — a tiny Rust static server is easy to add to `plinth-cli` later).

## Files

| File | What |
|---|---|
| `plinth-web.js` | Loads a core and an app module and links them side-module style: grows the core's exported table by the app's table import minimum, then instantiates `app.wasm` with `{ "plinth-rt": { ...rt exports without the prefix, memory, table, table_base } }`. No DOM code, so it is also what the Node tests exercise. |
| `protocol.js` | The op buffer / event wire format (SPEC.md §8.2, §8.4) in JS, byte-compatible with `crates/plinth-protocol`. Hand-written, not generated; keep it in sync by hand if the wire format changes. |
| `zip.js` | A tiny read-only zip reader for `.plnt` packages (stored or deflated entries), using the standard `DecompressionStream("deflate-raw")` (no dependency). |
| `ui-api.js` | GENERATED by `scripts/gen-web-ids.mjs` from `wit/plinth/ui-api.toml`. Re-run the script after the id table changes. |
| `dom-renderer.js` | The only DOM-specific file: a semantic tree built from the op stream, and a renderer for Screen/Section/Text/Heading/Button/TextField/Toggle/List/Row/Group/Empty plus a simple nav shell for primary screens (plain `<button>`/`<input>`/heading tags, no custom elements). |
| `style.css` | The runtime-owned look (SPEC.md §3: apps declare intent; the runtime owns layout, spacing, color). |
| `index.html` | `index.html?app=<url of .plnt>&core=<url of core.wasm>`. |
| `test/run-counter.mjs`, `test/run-todo.mjs` | Node 22 tests (same `WebAssembly` API as the browser) that exercise `plinth-web.js` and `protocol.js` directly, with no DOM. |

## What this spike does NOT do

- **Timers**: `time.set-timer`/`cancel-timer` are real (`setTimeout`/
  `setInterval`), but nothing in this tree drives the resulting `timer`
  events back into `app.onEvent` yet (no event loop wiring in
  `dom-renderer.js`). `time.now`/`monotonic-now` work.
- **Store** (`plinth:app/store@1.0.0`, `kv-get`/`kv-set`/`kv-delete`/
  `kv-keys`): stubbed. Every call returns `denied(unsupported)`, same
  shape a host with no store implementation returns (SPEC.md §11). A real
  implementation would back it with `localStorage`/IndexedDB.
- **Clipboard** (`read-text`/`write-text`): stubbed the same way, denied.
  A real implementation would use the async Clipboard API, which does not
  fit this interface's synchronous core-level calls without a JS-side
  cache or restructuring the import as async.
- **No static linking in the browser** (by design, SPEC.md §18.3): this
  means every app instantiation re-pays the cost of growing the table and
  wiring imports, which is fine for one app but not yet tested with many
  concurrently installed/browsed apps sharing one core instance.
- No asset loading (icons, images) and no accessibility tree (AccessKit on
  desktop vs. plain semantic HTML here — the HTML is semantic, but no
  parity testing was done against the desktop a11y output).
- No `plinth web <dir|file.plnt>` CLI subcommand; use `npx http-server`.
